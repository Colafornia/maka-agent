成功路径

  • checkpoint 写成功
  • 下一次请求携带短摘要
  • 继续正常 agent turn

失败路径（当前）

  • 摘要失败或输入仍超限
  • 保持原历史，记录 fail-open
  • 后续请求可能再次 overflow

建议把优化放在哪里？

优先改“请求怎么发”和“预算怎么算”；最后再改“失败时是否允许有损”。

高置信 · 先做

① 复用缓存前缀

摘要请求复用普通请求的 system、tools 和历史前缀，只在末尾追加一条 compact 指令。这样 provider 可以复用 KV cache。

对应节点：3 → 4
参考：Reasonix summaryRequest
高置信 · 先做

② 摘要预算跟窗口走

把固定 8000 改成 min(8192, max(window/4, 512))。小窗口不会被摘要本身挤爆，大窗口仍有上限。

对应节点：3 → 4
不应改变触发时机
高置信 · 先做

③ 留 5% 规划余量

估算不是 tokenizer 本人。给 framing、provider 字段和语言差异留 max(256, 5% window) 的安全垫。

对应节点：2 → 3
只影响规划，不替代 provider 判定
中高置信 · 第二批

④ 摘要失败也能脱险

正常摘要 → 缩短输入 → repair → 有损 truncate。canonical 历史不删，只写 durable projection，并明确标记 lossy。

对应节点：4 的失败分支
收益高，数据质量风险也最高
中高置信 · 第二批

⑤ 记住改过哪些文件

checkpoint 增加 readFiles、modifiedFiles，跨 checkpoint 累积。模型不用只靠摘要“自觉记住”。

对应节点：4 → 5
参考：Pi fileOps ledger
中高置信 · 第二批

⑥ 混合估算 + prune 门槛

用 provider usage 锚定已知部分，尾部再用 chars/4；只有预计一次 prune 能回收足够 token 时才动手。

对应节点：2 → 3
先补“预计回收量”指标

推荐落地顺序

  • 01缓存对齐 + cache hit/miss 观测
  • 02窗口联动 output budget
  • 035% planning reserve
  • 04usage anchor、prune 收益门槛、fileOps
  • 05最后再上线 lossy fallback 和插件 hook

看哪些指标判断有效？

  • →摘要请求的 cache hit tokens 是否上升
  • →每次 compact 实际节省多少 input tokens
  • →摘要失败、repair、overflow 的比例
  • →同一长会话的 compact 次数和总耗时
